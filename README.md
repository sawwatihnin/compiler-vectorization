# Compiler Optimizations: Vectorization

## Overview

This project adds two arrays of `float` values with a normal C loop. It demonstrates scalar execution, automatic SIMD vectorization, and how compiler reports can show whether vectorization happened.

## What Are SIMD and Vectorization?

SIMD means **Single Instruction, Multiple Data**. A scalar loop adds one pair at a time:

- Add `A[0] + B[0]`.
- Add `A[1] + B[1]`.
- Add `A[2] + B[2]`.
- Add `A[3] + B[3]`.

A vectorized loop uses a vector instruction to add several pairs together. A vector register holds multiple values, and the processor applies the same operation to its lanes. The number of values depends on the instruction set, vector width, and data type. For example, the Apple Clang report below says the loop vectorization width was 4, so each vector operation handles four loop elements.

Instruction-set names vary by processor family. x86 processors may use SSE or AVX instructions; Arm processors use SIMD extensions such as NEON. Different computers do not necessarily support the same vector instructions.

## How the Compiler Chooses Loops

The compiler analyzes loop dependencies, memory accesses, control flow, and estimated cost. It can vectorize a loop when iterations can safely run on groups of data together and the expected benefit is worth the generated code. If it cannot prove that memory accesses are independent, it may skip vectorization or create a runtime check and alternate loop paths. In the C function here, the pointers are not marked `restrict`, so the compiler must account for possible aliasing.

`-O2` and `-O3` enable broader optimization than `-O0`; these transformations can include vectorization and loop unrolling. More optimization does not guarantee that every loop is vectorized or that `-O3` is faster than `-O2`. Dependencies, uncertain aliasing, early exits, target support, code size, and the compiler's cost model can affect the decision.

## Requirements

You need Apple Clang (or another C compiler) and Bash. The benchmark script expects a command named `gcc`; on macOS this commonly invokes Apple Clang, not GNU GCC. Check with `gcc --version`. If the command is missing, install a compiler or change the compiler command in the script. GNU GCC is optional for the separate GCC example below. No external libraries are needed.

## Build and Run

Run these commands from the repository root:

```bash
clang -O0 vectorization.c -o vector_O0
./vector_O0

clang -O2 vectorization.c -o vector_O2
./vector_O2

clang -O3 vectorization.c -o vector_O3
./vector_O3
```

Each run checks every output element and prints a success message if all one million results are correct.

## Benchmark

Run the existing script from the repository root:

```bash
chmod +x benchmark.sh
./benchmark.sh
```

The script invokes `gcc` for all three builds. On this Mac, `gcc` can be Apple Clang; check `gcc --version` to know which compiler the script uses. GNU GCC can also run the script if installed and available as `gcc`.

The reported time covers the complete program: allocation, input initialization, array addition, checking the results, and freeing memory. It does not isolate the addition loop. These measurements are useful for a small demonstration, not a precise benchmark. System activity and compiler and hardware differences affect timing. The results below are from one run and do not show that `-O3` will always beat `-O2`.

## Experimental Evidence

### Apple Clang vectorization report

The Apple Clang optimization remarks are direct evidence that the compiler vectorized the array-addition loop; the benchmark times alone do not prove that. Re-create and save the report from the repository root with:

```bash
clang -O3 -Rpass=loop-vectorize -Rpass-missed=loop-vectorize -Rpass-analysis=loop-vectorize vectorization.c -o vectorized 2> results/vectorization-report.txt
```

The project report records vectorization width 4 and interleaved count 4 for the addition loop and the initialization loop. Width 4 means one vector operation processes four elements. Interleaved count 4 means the vector loop body contains four vector operations, so a full trip through that body can handle up to 16 elements; a remaining tail is handled separately. The correctness-check loop was not vectorized: Clang reported that it could not determine the number of loop iterations.

The checked-in `results/vectorization-report.txt` preserves the diagnostic text and identifies the compiler/target used for that capture. Diagnostics may differ on another compiler or target.

### Assembly

Generate assembly from the repository root:

```bash
clang -O3 -S -march=native vectorization.c -o results/vectorization.s
```

`-march=native` lets Clang use features available for the current machine. Assembly syntax and vector instructions vary by architecture. The checked-in file is evidence for its recorded target, not a promise that another computer produces identical instructions.

### Separate GNU GCC example

This is a GNU GCC example from a different test environment, not the Apple Clang benchmark run above. GNU GCC's vectorization report can be requested with:

```bash
gcc -O3 -fopt-info-vec-optimized vectorization.c -o vectorized
```

The reported output in that separate environment was:

```text
vectorization.c:6:23: optimized:
loop vectorized using 16 byte vectors

vectorization.c:6:23: optimized:
loop versioned for vectorization because of possible aliasing

vectorization.c:6:23: optimized:
loop vectorized using 8 byte vectors
```

Here, 16-byte vectors can hold four 4-byte floats and 8-byte vectors can hold two. Loop versioning means GCC made alternate paths so it can handle possible pointer overlap safely. This is separate compiler evidence and must not be treated as a measurement or diagnostic from the Apple M2 experiment.

## My Experimental Results

### Benchmark Results

All three versions passed the correctness check.

| Optimization | Real Time | User Time | System Time |
| ------------ | --------- | --------- | ----------- |
| `-O0`        | 0.311 s   | 0.014 s   | 0.006 s     |
| `-O2`        | 0.196 s   | 0.004 s   | 0.004 s     |
| `-O3`        | 0.171 s   | 0.004 s   | 0.004 s     |

In this one run, `-O3` was about 45% faster than `-O0`. This is one Apple M2 Mac run; it does not establish that `-O3` always outperforms `-O2`. Do not compare it directly with GCC results or timings from another machine.
